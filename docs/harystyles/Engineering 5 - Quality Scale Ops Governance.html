7.2 Test data & determinism

  • One seed set: db/seed/seed-content.json (writers, letters, notebooks, issues) feeds local development, staging demos, end-to-end tests and the design canvas, so names and moods never diverge again.
  • Factories in @hs/test-kit build valid aggregates by default (aWriter().approved().withPatrons(3)).
  • Time is always injected. Tests run in random time zones (TZ randomized per CI shard) to catch hidden local-time assumptions.
  • External gateways have in-memory fakes that implement the same port, plus a "chaos" mode (delays, duplicates, reordering).

7.4 CI quality gates (pull request)

  1. Typecheck · lint (including boundaries, no-Date in domain, copy voice lint) · format
  2. Unit + property + integration tests (sharded, random time zone)
  3. Generated contracts committed · openapi-diff clean · event schema compatibility
  4. Route policy test · IDOR suite · leak scanner · secret scan · dependency and license audit
  5. Migration lint (squawk) · module graph check · rule traceability report (rules without tests are listed; INV-* without a test fails the build)

Definition of done

Rule IDs referenced · tests at the right layers (including a negative authorization test) · scenario added if the change touches a feature boundary · docs updated (module README, rule index, handbook if a rule changed, ADR if a decision changed) · flags have an owner and expiry · observability (log/metric) for new background behavior · works in all 3 themes and 3 type pairs · accessible.

8.3 Design choices that scale

  • Stateless API and worker containers scale horizontally (ECS autoscaling on CPU and request count; workers on queue depth).
  • Lazy ration build means we never compute rations for inactive readers. Eager prebuild runs only for push opt-ins.
  • Anonymous traffic at the edge: public pages are cached at the CDN, so a viral letter costs almost nothing at the origin.
  • Counters off the hot path (§3.9i). Heartbeats are coalesced on the client (send on interval or page-hide only) and written with a single upsert.
  • Connection pooling: RDS Proxy (transaction pooling) between tasks and Postgres. Pool size per task is tuned so that total connections stay under 70% of the database's max_connections.
  • Read replica for writer pages, search, studio analytics and console reports. Reader-own data (Shelf, Tonight) always reads from the primary (read-your-writes).
  • Partitioning plan (triggered at ≥50M rows or a slowing vacuum): monthly range partitions (pg_partman) for reads, reactions (by created_at), ledger_entries, audit_log, outbox_events, notifications.
  • Fan-out on publish (notifications to patrons and followers) is batched in jobs of 1,000 recipients with dedupe keys, never done in the request.

Extraction criteria for turning a module into its own service (ADR required): a different scaling profile proven by metrics, or a different security or compliance boundary, and a stable public interface for 3+ months. Likely first candidates: media/card rendering (CPU-heavy) and notifications fan-out.

8.5 Cost guardrails

  • Monthly infrastructure budget alarms per environment (MVP production target: roughly $1.5–3k/month at M12 scale; staging ≤ 30% of production; previews auto-expire).
  • Unit metric: infrastructure cost per monthly active reader, reviewed monthly. Investigate if it grows faster than MAU.
  • No always-on resources without a tag for owner and cost center (Terraform-enforced).

9.2 Delivery pipeline

  1. Trunk-based development: short-lived branches; main is always releasable. Unfinished work ships behind release flags.
  2. Merge → build images (api, worker, web, console, all tagged with the git SHA) → deploy to dev → smoke tests.
  3. Promote the same images to staging: migrations, end-to-end suite, nightly billing suite.
  4. Production promote (manual approval, during business hours): run migrations (a separate task, migrator role) → blue/green deploy for api and web (CodeDeploy) with canary 10% for 10 min → automatic rollback on alarm (5xx rate, p95, error budget burn) → workers rolled after the API.
  5. Every deploy is recorded (SHA, migrations, flags changed) and annotated on dashboards.

9.3 Database migrations

  • Forward-only, numbered SQL files, reviewed by a CODEOWNER. Never edited once merged. Mistakes are fixed by a new migration.
  • Expand/contract: (1) add the new structure, nullable or with a default; (2) deploy code that writes both and reads the new one; (3) backfill with a resumable job; (4) enforce constraints (NOT VALID then VALIDATE); (5) remove the old structure ≥ 2 releases later, and only after the oldest supported mobile version no longer needs it.
  • Every migration must be compatible with the currently running code (N−1). Session settings: lock_timeout = '5s', statement_timeout appropriate to the change. Indexes are built CONCURRENTLY.
  • squawk lint in CI. A timing rehearsal on staging snapshot data is required for any table over 1M rows.

9.4 Mobile releases

  • Weekly release train: branch cut Monday → QA (Maestro + manual exploratory) → submission Wednesday → staged rollout 10% → 50% → 100% over 3 days, watching crash-free sessions (≥ 99.5%).
  • Over-the-air updates (EAS Update) only for JavaScript bug fixes compatible with the installed native build and within store policies. Never to change business behavior, which is server-side anyway.
  • Version support: bootstrap.minSupportedVersion. Versions are supported for 90 days, then soft-prompted, then hard-blocked (426) only for security or breaking reasons.
  • Kill switches (ops flags) for risky client features, e.g. reader.save-as-card, mobile.offline-cache.

9.6 Backups & disaster recovery

  • RDS: point-in-time recovery for 35 days. Daily snapshots copied cross-region, kept 90 days. Monthly snapshots kept 1 year. S3: versioning plus cross-region replication for media and exports. Redis is never authoritative.
  • RPO 5 min · RTO 2 h. A restore drill every quarter: restore to a fresh instance, run integrity checks (ledger balanced, row counts, a sample of letters rendered), record the time taken.
  • A regional outage runbook exists: Terraform applies to the backup region, the restored snapshot is promoted, DNS fails over, provider webhook URLs are updated.
  • Integrity jobs run nightly: ledger balance per currency, entitlement reconcile, charges ↔ Stripe reconcile, payouts ↔ transfers reconcile. Any drift pages finance and on-call.

9.8 Incidents & runbooks

Severity: SEV1 data leak, money error or full outage · SEV2 major feature down or SLO breach · SEV3 degraded. On-call rotation with a primary and a secondary. The incident commander uses a status page and keeps a comms log. A blameless postmortem is written within 5 working days, with actions tracked to completion.

10.3 Ownership

  • CODEOWNERS maps every module, package, migration folder and infrastructure path to an owning person or team. Each module has a named owner, who keeps its README, tests and rule references healthy.
  • Cross-cutting owners: Security (auth, policies, secrets), Platform (infrastructure, CI, observability), Finance engineering (billing, ledger, payouts), Design systems (tokens, UI packages, modes and pairs).
  • High-risk paths require two approvals, one from the owner: billing/, ledger/, identity/, */domain/policies.ts, db/migrations/, infra/, packages/contracts/.

10.4 Working conventions

  • Conventional Commits. PR titles reference the rule or ticket. The PR template asks: rule IDs touched · migration? (expand/contract step) · security checklist (Part 4 §6.11) · screenshots in 3 themes for UI changes · flags added (owner, expiry) · docs updated.
  • Small PRs (aim for under 400 changed lines, excluding generated code). One module per PR unless an ADR covers the cross-module change.
  • Reviews check: is the rule in its single home? Is there a test named after it? Could this break another feature? (Check the FX matrix.)

10.5 Changing a business rule safely

  1. Update the rule in Part 1 (new rule, or a changed one with a revision note). Bump the handbook version.
  2. Find the rule's single home in the rule index. If the logic exists anywhere else, that's a bug: remove the duplicate first.
  3. Find tests by rule ID (grep "BR-XX-NN"). Change the tests first so they describe the new behavior.
  4. Check the feature interaction matrix and scenarios for rows involving the rule. Update or add FX/SC tests.
  5. Implement behind a release flag if the change is user-visible or touches money.
  6. Check API and event compatibility (additive only). Plan migrations with expand/contract.
  7. Ship to staging, run the scenario suite, roll out the flag gradually, monitor the metrics tied to the rule, then remove the flag.

10.6 Guardrails for AI agents and new contributors (AGENTS.md)

Read first

This handbook's Part 1 (rules and invariants), Part 4 §4.2–4.4 (module anatomy and rule index), the target module's README, and the relevant ADRs.

Always

  • Work inside one module unless the task names several. Put logic in the rule's single home.
  • Reference rule IDs in code comments and test names. Add or update tests at the right layer, including negative authorization tests.
  • Run before proposing changes: pnpm typecheck && pnpm lint && pnpm test --filter <module> && pnpm contracts:check.
  • Regenerate contracts when schemas change, and commit the generated files.
  • Update the module README, the rule index and the handbook when behavior changes.
  • State assumptions in the PR description. Ask when a rule is ambiguous; don't guess.

Never

  • Edit an applied migration, write UPDATE/DELETE against ledger, audit or append-only tables, or drop columns without the expand/contract plan.
  • Add a route without a policy, return ORM rows directly, or add counts, legal identity or patron body to reader-facing DTOs.
  • Duplicate a rule in a client or another module. Compute money with floats. Call Date.now() in domain code.
  • Call external services inside a database transaction, or skip idempotency keys on money, message or report operations.
  • Add a runtime dependency without the dependency checklist. Disable a lint rule, test or CI gate to get a build passing.
  • Read production data or secrets. Agents work only with seed data and test-mode credentials.

Human approval is required for

Changes under billing/, ledger/, identity/, policies, migrations, infra/, packages/contracts/, and any change to Part 1 rules or invariants.

10.8 Review cadence

  • Weekly: error budget, invariant alerts, flag expiries.
  • Monthly: dependency health, cost per MAU, rule traceability report (rules without tests), open security findings.
  • Quarterly: architecture review (module graph, extraction candidates, ADR review triggers), access review (staff roles, IAM), restore drill, game day, handbook currency check.
  • Yearly: threat model refresh, penetration test, PCI SAQ-A, privacy review of data flows and processors.
