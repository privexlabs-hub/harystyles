3.1 Conventions

  • Tables are plural snake_case. Primary key id uuid, a UUIDv7 generated by the application (time-ordered, index-friendly, unguessable enough that IDs aren't enumerable, though security never relies on that).
  • Every table has created_at timestamptz not null default now(). Mutable tables also have updated_at, maintained by a trigger.
  • Enumerations are text + CHECK constraints (easy, lock-free migration), mirrored by Zod enums in @hs/contracts. A test asserts the two lists match.
  • Money: amount_minor bigint + currency char(3). Never numeric on its own, never float.
  • Times: always timestamptz (UTC). Local wall-clock values are date/time + an IANA timezone text.
  • Case-insensitive identifiers (email, slug) use citext.
  • Foreign keys always. ON DELETE RESTRICT by default; CASCADE only for pure child rows (e.g. issue slots), and declared in the table notes.
  • Each table has one owning module. Only that module writes it (§3.4). Reads across modules go through the owner's public interface or a documented read-only view.

Why both patronages and entitlements? A patronage is the commercial relationship and has billing states. An entitlement is the access fact. Access can come from several sources (Stripe, a future in-app purchase, gifts, comps), so canRead reads one table with one index, whatever the source. Entitlements are written only by the billing module when it applies patronage changes. A nightly entitlement.reconcile job recomputes them from patronages and alerts on any difference.

3.7 Transaction boundaries

The rule: one use case = one database transaction, which changes one aggregate and inserts its outbox events. Never call an external service inside a transaction. Never span two modules' writes in one transaction: the second module reacts to the event.

Isolation: READ COMMITTED by default. Correctness comes from unique constraints, SELECT … FOR UPDATE on the aggregate root, and optimistic version columns, not from SERIALIZABLE. Deadlock avoidance: lock aggregates in a fixed order (reader → writer → letter), and keep transactions under 100 ms.

3.9 Data structures & algorithms

a) Letter document and sentence anchors

The body is a ProseMirror JSON document defined by @hs/editor-schema. Every block node gets a stable id (nanoid, 10 characters) when it's created, and keeps it through edits, splits (the second half gets a new ID) and moves. At publish the server derives:

  • body_text: plain text with block separators (used for search, preview and word count).
  • anchors: for each block, sentences from Intl.Segmenter(locale, { granularity: "sentence" }). Each sentence becomes { id: blockId + ":" + h8, blockId, start, end, h8 }, where h8 is the first 8 hex characters of SHA-256 of the normalized sentence (NFKC, lowercase, collapsed whitespace).

Re-anchoring on republish (EX-12), per old anchor:

1. same blockId and same h8 exists in new revision  → keep id (exact)
2. same blockId: best new sentence by trigram Jaccard similarity ≥ 0.6 → remap id
3. any block: exact h8 match (sentence moved) → remap id
4. otherwise → mark reactions orphaned (kept in writer totals, not highlightable)
Cost: O(S) hashing + O(Sb²) per block for step 2 (Sb = sentences in a block, small) → linear in practice.

b) Lamp time

lampAt(reader, localDate):
  p = preferences(reader)
  if p.lamp_mode == 'fixed': t = p.lamp_fixed_time
  elif p.geo_cell is null:   t = 18:00
  else: t = clamp(sunsetNOAA(centroid(p.geo_cell), localDate, p.timezone), 17:00, 21:30)
  return toInstant(localDate, t, p.timezone)   // Temporal: 'compatible' disambiguation
                                               //  gap → shift forward, overlap → earlier (EX-02)

The NOAA solar position algorithm is pure, deterministic, and unit-tested against published sunset tables for 20 cities over a year (±2 minutes).

c) Evening date

eveningDate(reader, now):
  tz = preferences(reader).timezone
  today = toLocalDate(now, tz)
  return now >= lampAt(reader, today) ? today : today.minus(1 day)
nextLamp(reader, now):
  e = eveningDate(reader, now); return lampAt(reader, e.plus(1 day))

The function is pure and takes an injected Clock. reader_schedule caches next_lamp_at and is recomputed after each lamp and on every preference change.

d) Ration builder (BR-RA-05)

build(reader, e, mood):
  issue    = curation.getIssue(e, mood) ?? curation.evergreenIssue(e, mood)
  excluded = ration.completedLetterIds(reader)           // set, O(1) lookup
  blocked  = engagement.blockedWriterIds(reader)         // set
  used     = ∅ writers; slots = []
  eligible(l) = l.status=='published' ∧ l.id∉excluded ∧ l.writer∉blocked ∧ l.writer∉used
                ∧ (l.visibility=='public' ∨ entitlements.canRead(reader, l.writer))

  // 1) personal slots: patrons first, then follows; published in last 48h; max 2
  personal = (letters of patronized writers ∪ letters of followed writers) where published_at ≥ now-48h
  sort personal by (isPatron desc, published_at desc, hash(reader,l.id,e) asc)   // deterministic
  for l in personal while |slots| < 2: if eligible(l): take(l, source)

  // 2) issue slots in curated order, then evergreen backfill, then adjacent moods (EX-04)
  for l in issue.letters ++ evergreen(mood) ++ evergreen(adjacent(mood)):
    if |slots| == 5: break
    if eligible(l): take(l, sourceOf(l))

  assert invariants(slots)        // INV-07: distinct writers, eligibility; throws → alert
  return { slots, short: |slots| < 5 }
Complexity: O(P log P + I + E), P ≤ ~200, I = 5, E ≤ pool size scanned until filled.

Determinism matters: the same inputs always give the same ration, which makes property tests and incident replay possible.

e) Read detection

Clients send batched heartbeats every 15 s while the letter is in view: {letterId, rationId?, maxProgress, activeSeconds}. The server clamps activeSeconds to the wall-clock time since the previous heartbeat plus 2 s, keeps the maximum progress (monotonic), and sets completed_at once BR-RA-08 is met. This is an idempotent upsert on reads, and ration slot read_at is set in the same transaction.

f) Money allocation (BR-LD-02)

allocateFee(lines[], fee):              // largest remainder method, integers only
  total = Σ lines.amount
  raw_i = fee × lines_i.amount / total
  alloc_i = floor(raw_i); remainder = fee − Σ alloc_i
  give +1 to the `remainder` lines with largest fractional part (tie: lower line id)
split(line):
  net = amount − alloc − tax
  platform = roundHalfEven(net × 10 / 100); writer = net − platform
Invariants (property-tested with fast-check):
  Σ alloc_i == fee;  platform + writer == net;  all values ≥ 0 for amount ≥ fee+tax;  deterministic.

g) Entitlement check

canRead(reader, letter):
  if letter.visibility == 'public' and letter.status == 'published': return FULL
  if reader?.id == letter.writer_id: return FULL
  if reader and activeEntitlementUntil(reader.id, letter.writer_id) > now: return FULL
  return PREVIEW
activeEntitlementUntil: Redis ent:{r}:{w} (TTL 60s) → else
  select max(valid_until) from entitlements where reader_id=$1 and writer_id=$2 and status in ('active','grace')

h) Rate limiting

Sliding-window counters in Redis (a sorted set, or GCRA via @fastify/rate-limit), keyed by {route-class}:{user|ip}. Business quotas that must be exact (e.g. 3 messages per writer per day, BR-EN-04) are checked in Postgres inside the use-case transaction, not in Redis.

i) Aggregated writer stats

Reaction and kept-line writes add the letter ID to a Redis set stats:dirty. Every 5 minutes stats.aggregate pops the set and recomputes each dirty letter's row in letter_stats with one grouped query. This avoids hot-row contention on popular letters and keeps counts out of the reader write path entirely.

j) Search

search_vector = setweight(title,'A') || setweight(pen_name,'A') || setweight(subtitle,'B') || setweight(public_body,'C'). For patron letters, the body weight is always empty (INV-18): the indexer builds the vector from renderForViewer(anonymous). Ranking: ts_rank_cd, then published_at desc. There is no popularity signal. Writer lookup uses trigram similarity on the normalized pen name.

k) Pagination cursors

Opaque base64url of {sortKey, id}, signed with HMAC so clients can't tamper with them. Queries use WHERE (sort_key, id) < ($1, $2) ORDER BY sort_key DESC, id DESC LIMIT n+1.

3.10 Migration rules (summary; full process in Part 5 §9.3)

  • Forward-only SQL files, never edited after they've been merged. Down-migrations aren't relied on; we roll forward.
  • Expand → migrate → contract across at least 2 releases for any rename, drop or type change.
  • CREATE INDEX CONCURRENTLY; lock_timeout = '5s'; new NOT NULL columns get a default or are backfilled by a job first.
  • Large data changes run as resumable worker jobs, not inside migrations.
