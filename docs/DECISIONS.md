### ADR-021 — One Next.js app hosts the UI and the server modules

**Context.** Docs 02 §2.3 put a Fastify API behind a thin Next.js BFF that "must not access the database". The brief for this build specifies Next.js Server Actions, Route Handlers and Neon.

**Decision.**
- The modular monolith lives in `src/server/modules/<module>/{domain,application,infra,index.ts}`, with the same module list and the same rule homes as docs/04 §4.2–4.4.
- Pages and actions import modules only through `index.ts`, plus explicitly shared pure domain files such as `ration/domain/time.ts`.
- Domain code is pure and takes time as an argument.
- `server-only` blocks any module from reaching a client bundle.
- Server Actions serve our own UI. JSON Route Handlers live under `/api/v1/*`.

**Consequences.**
- Mobile (Milestone B) needs a versioned JSON API. The services are already framework-free, so extracting `/v1` routes or a separate service is mechanical.
- Contract generation (zod → OpenAPI) is deferred until a second client exists.

### ADR-022 — Self-hosted Better Auth on our Neon database

**Context.** BR-ID-01 requires magic link, passkey, Google and Apple sign-in, and no passwords. We checked Neon Managed Auth on 2026-10-25, against the docs and the official `neon-auth` skill:
- Its quick-start documents email/password.
- Its plugin matrix lists Passkey as *not exposed*.
- Its social providers are Google, GitHub and Vercel, with no Apple.

**Decision.**
- Run self-managed `better-auth@1.7` with the magic-link plugin and `@better-auth/passkey`. Google and Apple activate when credentials are set.
- Use the Drizzle adapter on our own tables (`users`, `sessions`, `accounts`, `verifications`, `passkeys`). App fields such as status, age attestation and onboarding are Better Auth `additionalFields`.
- Magic-link tokens are stored hashed, expire after 15 min, and are single-use.
- The magic-link rate limit is 5/min (configurable).
- Sessions are 30-day rolling.
- Account linking happens only for trusted providers with verified email (BR-ID-02).

**Consequences / deviations from docs/06 §6.2.**
- The cookie is `hs.session_token`, not `__Host-hs_sid`.
- There is no 90-day absolute session cap and no refresh-token family for mobile yet.
- Step-up re-auth (BR-ID-05) is not implemented. That is fine for Milestone A, which has no email change, deletion or staff break-glass.

### ADR-023 — Neon Postgres with a pooled `pg` driver

**Decision.**
- The runtime uses `drizzle-orm/node-postgres` over a `pg` `Pool` against Neon's **pooled** URL, with a 5 s statement timeout and a 3 s lock timeout.
- The domain needs interactive transactions (`SELECT … FOR UPDATE`, `INSERT … ON CONFLICT … RETURNING`, deferred constraint triggers). Neon's one-shot HTTP driver cannot run those, so it is not used.
- Migrations use `DATABASE_URL_UNPOOLED`.
- Required extensions are `citext` and `pg_trgm`, both available on Neon.
- Migrations are generated by drizzle-kit and are forward-only. Hand-written SQL (`0000_extensions`, `0002_guards`) carries what Drizzle can't express: append-only triggers, deferrable constraints, and the 5-slot issue trigger.

### ADR-024 — Postgres instead of Redis (Milestone A)

Rate limits use a fixed-window table (`rate_limits`). Entitlement checks query Postgres directly. Writer stats are recomputed from recent activity, with no dirty set. Redis can return when lamp-hour load (docs/08) demands it.

### ADR-025 — Jobs as idempotent functions behind an authenticated endpoint

**Decision.**
- The jobs `outbox.relay`, `letter.publish-scheduled`, `issue.lock` (lock + evergreen autofill) and `stats.aggregate` are plain functions in `src/server/jobs.ts`.
- They run through `pnpm job <name>`, or `POST /api/internal/jobs/<name>` with `Authorization: Bearer $JOBS_SECRET` (constant-time compare; 404 otherwise).
- In production a Neon schedule trigger or the host's cron calls them.
- No business logic is duplicated in a Neon Function.

**Note.** Tonight is built lazily on request (docs/03 §3.7), so a missed job never breaks reading.

### ADR-026 — Neon Object Storage for media (not yet implemented)

**Decision.** Use the S3-compatible Neon Object Storage behind an `ObjectStore` port:
- private quarantine bucket
- presigned PUT
- server-side magic-byte check and re-encode with `sharp`
- promote to the public or private bucket

**Status.** Not started. Milestone A ships without images (avatars are generated initials). The Neon project exists now, so the next step is declaring private/public buckets in `neon.ts`. Tracked in [PRODUCT.md](./PRODUCT.md).

### ADR-027 — Out of Milestone A scope

These stay out of this release: payments and ledger posting (Stripe), messaging, moderation, push, mobile apps, AI features, and Realtime.
- The AI Gateway is not used. No product requirement calls for generation (D8 only needs the `ai_assisted` disclosure flag), and the gateway is unavailable on the Neon Free plan.
- The pure money core (`src/server/money`, BR-LD-01/02) **is** built and property-tested, so billing in Milestone B starts from verified arithmetic.
- The curation console is a role-gated route group, not a separate origin with hardware-key MFA (docs/06 §6.2).

### ADR-028 — PGlite for local development and tests

Docker isn't available on the build machine, and Testcontainers needs it. Local dev and integration tests use **PGlite** (Postgres 17 compiled to WASM) via `DATABASE_URL=pglite:<dir>` or `pglite:memory`, with the same migrations. The data directory lives under `node_modules/.cache/harystyles/`. Inside the project tree, its file writes trigger Turbopack's watcher and cause a reload loop.

**Trade-off.** PGlite is single-connection, so true concurrency (SC-01) is exercised logically, not under parallel connections. Neon runs Postgres 18 and PGlite runs 17. Both apply the same migrations; SC-01 concurrency was verified manually on Neon. Automating the integration suite against a Neon `test-*` branch is the next step.
